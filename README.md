# Chai & Change: café billing

Billing and GST invoicing for Indian cafés. You enter your menu card (items with sizes, variants and add-ons), bill customers at the counter, and print or WhatsApp the invoice using a small template library.

- **Next.js 16** (App Router, Cache Components, `proxy.ts`), React 19, Tailwind 4
- **Appwrite TablesDB** (free tier) for data
- **Clerk** for sign-in

## Setup

```bash
bun install
bun run dev
```

`.env` needs:

| Key | What |
| --- | --- |
| `APPWRITE_API_KEY` | Server API key with `tables.read`/`tables.write` and `files.read`/`files.write` (for item photos) on the project. Server-only. |
| `NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY` | From the Clerk dashboard |
| `CLERK_SECRET_KEY` | From the Clerk dashboard. Server-only. |

The project id and endpoint live in `appwrite.config.json`.

First run: sign up, fill in **Settings** (café name, GSTIN, FSSAI, state), add the built-in Baithakkhana menu (45 items, from `lib/sample-menu.ts`) or build your own under **Menu**, then bill from **Counter**. New cafés print on the 80 mm counter receipt by default.

## Database: schema as code + migrations

Drizzle can't target Appwrite's free TablesDB: it needs a SQL connection, and Appwrite's dedicated Postgres is a Pro-plan feature. The same workflow is done with Appwrite's own tooling:

| Drizzle | Here |
| --- | --- |
| `schema.ts` | `db/schema.mjs`, the single source of truth |
| `drizzle-kit push` | `bun run db:push` (`appwrite push table`) |
| typed ORM client | `lib/appwrite/generated`, generated by `appwrite generate` |

```bash
# edit db/schema.mjs, then:
bun run db:migrate   # build appwrite.config.json → push to Appwrite → regenerate the typed SDK
```

`db/schema.mjs` also declares the `item-photos` storage bucket (`appwrite push bucket`). Adding a column is safe on a live database; to avoid a forced push, the columns for paid/due, bill edits and photos were added one by one with the SDK (`createEnumColumn`, `createDatetimeColumn` and so on), then `db:build` and `db:generate` were run so the config and typed client match.

Usage: `tables.invoices.list({ queries: q => [q.equal("ownerId", id), q.orderDesc("issuedAt")] })`. Field names in queries are type-checked.

**Access model.** Tables have no client permissions. Every read and write goes through the server API key in server components and server actions, scoped to the Clerk `userId` stored in `ownerId`. Ownership is checked in `lib/data.ts` and `lib/actions/*`. Auth is resource-based: `requireUser()` runs in every data function and action, and `proxy.ts` only handles the Clerk session.

## India-specific billing rules

- Money is computed in integer paise. A discount is applied before tax, so it reduces the taxable value. Totals round to the rupee, with a round-off line.
- Regular dealers get a **Tax Invoice** with CGST and SGST each at half the rate (5% → 2.5% + 2.5%), under **SAC 9963**. There's an option for menu prices that already include GST (tax is worked out backwards).
- Composition dealers get a **Bill of Supply** with no tax lines, plus the mandatory declaration. Unregistered cafés get a plain invoice.
- Invoice numbers follow `PREFIX/26-27/0001`. The serial restarts each financial year (April–March, IST) and never exceeds Rule 46's 16-character limit. A unique index on (owner, FY, serial) prevents duplicates when two counters bill at once.
- Each invoice stores a snapshot of the café's details and line prices, so later edits to settings or the menu never change past bills.
- Amounts in words use lakh and crore. A UPI "scan & pay" QR is pre-filled with the bill amount. No service charge is added (CCPA guidelines, upheld by the Delhi HC in 2025).

## Templates

| Id | Paper | For |
| --- | --- | --- |
| `classic` | A4 | Full Rule 46 GST invoice for business customers |
| `thermal80` | 80 mm roll | Standard counter receipt |
| `thermal58` | 58 mm roll | Bluetooth/kiosk printers |
| `modern` | A5 | Branded dine-in bill, good for WhatsApp |
| `gstboxed` | A4 | Fully ruled tax invoice with an HSN/SAC tax summary, adapted from an [MIT-licensed GST template](https://huggingface.co/spaces/Nra/sbn_invoice/blob/main/Invoice_visualpath.html) |
| `simple` | A4 | Light single-box invoice, adapted from [sparksuite/simple-html-invoice-template](https://github.com/sparksuite/simple-html-invoice-template) (MIT) |

Licence notices for the two adapted layouts are in [THIRD_PARTY_NOTICES.md](THIRD_PARTY_NOTICES.md).

`thermal80` is the default for new cafés. Switching layout on a saved bill is saved to the bill and recorded in the `invoice_events` table. The bill page lists it under "Bill history" on screen, along with item edits and payment changes; the history never prints.

**Logo.** Upload one under Settings → Logo. The browser removes a flat background colour (when all four corners match), crops to the logo, shrinks it to fit 640×320 and saves it as WebP in the `settings.logo` column (`mediumtext`, at most 200 KB). Every template prints it at the top; the thermal ones show it in greyscale because that's how a thermal head prints. The logo isn't copied onto each bill, so changing it changes the logo on old bills too.

On thermal rolls, the page height is measured at print time so the printer doesn't feed blank paper. In the print dialog, choose your thermal printer and set margins to **None**.

## Counter flow: kitchen slip first, paid later

This follows how Indian POS systems handle a KOT (kitchen order ticket): the kitchen gets its ticket as soon as the order is taken, and the bill is settled afterwards.

1. Tap items on the counter. Dine-in orders need a **table number**; the bill won't save without one, on screen or on the server.
2. **Payment** is **Due** by default. Choose **Paid** (then UPI, cash, card, mixed or other) only if the guest pays up front.
3. **Save and print kitchen slip** saves the bill and opens it with the kitchen slip already printing. **Save without a kitchen slip** is there for takeaway orders that need no cooking.
4. When the guest pays, open the bill (Today lists due bills in red) and tap **Mark paid by** UPI, cash, card, other or **Mixed**. A wrong tap can be undone with **Mark as due**. Both are recorded in the bill's history.

Bills saved before paid/due existed count as paid. The printed bill says "Payment due" (DUE on receipts) until it's paid.

**Kitchen slip.** No prices: the order number in large type (the last part of the bill number, so INV/26-27/0042 is order 42), dine-in table or takeaway, date and time, and each item with its quantity, size, add-ons and notes. It prints on an 80 mm roll, or 58 mm when the bill's layout is the 58 mm receipt. Reprint it any time from the bill's **Kitchen slip** button.

**Mixed payment.** For a bill paid partly one way and partly another, choose **Mixed** and type the amounts for cash, UPI and card. One field (UPI at first, shown with a dashed border) isn't typed: it always holds the rest of the bill, so the parts add up. Typing in that field hands the job to another one. The server checks the parts equal the total. The bill, the ledger and the history show "Cash ₹200 + UPI ₹150"; the amounts are saved in `invoices.paymentSplit`. If a paid mixed bill is edited and its total changes, the cash part takes the difference (`rebalanceSplit` in `lib/billing.ts`).

## Expenses

**Expenses** is a sheet per day (IST). The first line is the day's collection: paid bills made that day, split by cash, UPI and card. Each expense below it has what it was for, the amount, and a **Balance left** column that carries down the sheet, ending in "Left after expenses". Use the arrows or the date box to write expenses for an earlier day. Today's page shows the day's expenses and what's left.

## Reports

**Reports → Collection** shows cash, UPI, card and the total collected for a week (Monday to Sunday), a month or a year, with arrows for earlier periods and a box for any dates. The year is the financial year, April to March, like the bill numbers. Below is a table day by day (month by month for a year) with expenses and what was left. A bill counts on the day it was made, once it's paid; a mixed bill adds each part to its own column.

**Reports → Items sold** lists every item with how many went out and for how much, for a day, week, month, year or any dates. Search an item ("water") to see its count; open it for the count on each date. It counts all bills, paid or due, by the item name on the bill.

To keep reads low, each finished day is added up once and kept as one row in `day_totals` (`lib/reports.ts`). A report reads those rows and goes back to the bills only for today and for days with no row yet. Any action that changes a past day's bill or expense must call `dayChanged(userId, day)` before and after the write, which deletes that day's row. "Add them up again from the bills" under the Collection table clears the kept rows for the dates shown.

## Editing a bill

**Edit items** on a bill opens it in the counter. Add or remove items, change quantities, the table, guest details, discount or note, then **Save changes**. The bill keeps its number and date. Lines already on it keep the price they were billed at, even if the menu price has changed since; new lines are priced from today's menu. The tax rate, and whether prices include GST, stay as they were when the bill was issued.

If items changed, a **changes slip** prints straight away, listing ADD and CANCEL with quantities, so the kitchen doesn't make the whole order again. The bill's **Changes slip** button reprints the latest one. Every edit is kept in the bill's history with what was added and removed and the old and new totals. If that record can't be written, the edit is undone.

## Item photos

Add a photo to any item in the menu editor. The browser crops it to a centred square and shrinks it to 480 px WebP (usually 20 to 60 KB) before upload. Photos show on the counter tiles and in the menu list; they never print.

Photos are kept in a private Appwrite storage bucket (`item-photos`: 1 MB limit, JPG/PNG/WebP, encrypted, virus-scanned). The browser never talks to Appwrite. `/menu/photo/[id]` checks the photo belongs to one of the signed-in café's items, then streams it. The image type is read from the file's bytes, not its name. Replacing a photo uploads a new file with a new id, so the browser can cache each one for a year. Removing an item, or its category, deletes its photo.

## Menu from Excel

On the Menu page, **Download menu** gives an .xlsx with one row per item: Category, Item, Price, Type (Veg, Non-veg, Egg), Available (Yes, No), Sizes and Add-ons (written as `Small = 120; Large = 160`), and Description. Edit it in Excel or Google Sheets and **Upload sheet**, as .xlsx or .csv. The file type is read from its contents, not its name, since phones often drop the extension; an old .xls gets a message saying how to re-save it. Before anything is saved, a review lists new categories, new items, every change per item, and rows that couldn't be read, with their row numbers. Items are matched by name, so renaming one in the sheet adds it as a new item. Items missing from the sheet stay unless you tick "Remove them". A blank Category cell uses the category of the row above. Uploading the same sheet twice changes nothing the second time. The sheet is read with `read-excel-file` and written with `write-excel-file` (both MIT).

## Bills and export

On Today and on the Bills page, paid bills are on a green line with how they were paid, and due bills on a red one. Today's header splits the day into money collected and money still due, and "Takings by payment" counts paid bills only, so it matches the cash drawer.

The Bills page filters by search and by IST date range, with Today, This month, Last month and This financial year as shortcuts. When a date range is set, it shows the takings and GST for that range. **Download CSV** exports the bills matching the current filters, oldest first, one row per bill. Each row has the invoice number, date (dd-mm-yyyy), document type, customer GSTIN, place of supply, status (Paid or Due), payment mode, the amounts paid in cash, by UPI, by card and other, taxable value, GST rate, CGST, SGST, round off and total. The CSV route is `/invoices/export?from=YYYY-MM-DD&to=YYYY-MM-DD&q=…` and returns at most 50,000 bills.

## Caveats

- Deleting an invoice leaves a gap in the serial numbers. GST expects consecutive numbering, so delete only bills made by mistake. The proper fix for a wrong bill is a credit note, which isn't built yet.
- One GST rate per café. That's right for a standalone café (5%). Items taxed differently, such as packaged MRP goods, aren't modelled per item.
- The dashboard's "today" stats scan up to 5,000 bills.
- Appwrite pauses free projects that see no requests for a while, and the whole site stops loading data until it's restored from the Appwrite console. To prevent that, Vercel Cron calls `/api/keep-alive` once a day at 09:00 IST (`vercel.json`), which makes one tiny read. It needs a `CRON_SECRET` environment variable on Vercel; Vercel sends it as a bearer token and any other request gets a 401.
- Appwrite bills database reads per row returned, so the app is built to read little. Links don't prefetch (`components/link.tsx`, and `partialPrefetching` is off in `next.config.ts`): every page reads the signed-in café's data, so each prefetch rendered the whole destination page on the server, and a navigation rendered twice. The menu and café settings are cached per café (`lib/data.ts`) and cleared by the menu and settings actions through `lib/cache-tags.ts`; bills are always read live. Import links from `@/components/link`, not `next/link`, and call `menuChanged()` or `settingsChanged()` from any new action that edits the menu or settings.
- Editing changes an issued bill in place. That's fine for an order still at the table. Once a bill has gone to a business customer for their GST input credit, correct it with a credit note instead (not built yet).
